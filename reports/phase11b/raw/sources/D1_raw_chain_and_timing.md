### 1.2 Compute/storage burden estimate for a daily BTC metric series, 2015–2024

Basis for the estimate (not independently benchmarked this session — engineering judgment from the figures above):
- Raw chain size at 2024 tip: ~650–700 GB unpruned; IBD on modern NVMe: hours to ~1 day, dominated by CPU (script/signature validation) once I/O is fast.
- If done from a **local full node + txindex**: one-time IBD (~1 day) + custom block-by-block parse to resolve prevouts (either via `getrawtransaction`/`gettxout` calls per input, or a self-maintained UTXO shadow index) + aggregation into daily bins. This is a multi-day (not multi-week) one-off job on a single modern machine (16-core / NVMe, matching the local hardware available here), then trivially incremental.
- If done via **AWS Public Blockchain Data** (Section 3): the address/value-per-input join is already done; a `date=2015-01-01 .. 2024-12-31` slice of `btc.transactions` can be read directly from S3/Athena with no node operation at all — this removes essentially all of the "raw reconstruction" burden for Bitcoin, at the cost of depending on a third party's (open-source, but unaudited-by-us) ETL correctness and an "experimental, not for production" disclaimer.

### 2.2 Compute/storage burden estimate, 2015–2024

- **Logs/token_transfers/transactions/receipts only** (no historical `eth_call` state, no traces): a full node (Erigon or Geth) with default history retention, ~1–2 TB disk, feasible on the local machine (244 GB free is **not** sufficient headroom for a full Ethereum node from genesis today — this alone rules out running a fresh full/archive Ethereum sync locally on the current disk budget). IBD for a full node is materially faster and cheaper than an archive sync.
- **Historical state / traces at arbitrary past blocks**: requires archive-class infrastructure (Erigon/Reth ~2–4 TB current, legacy Geth hash-based >12 TB) — not feasible on this machine's 244 GB free disk at all.
- **AWS Public Blockchain Data removes this constraint entirely** for the metrics this project would plausibly want (transactions, logs, token_transfers, traces): it is produced upstream from an Erigon archive-capable node and republished as Parquet, so a 2015–2024 daily series can be built by reading S3/Athena directly, with no local node and no local archive disk footprint. This is the single most important reconstruction-feasibility finding of this audit (see §3 and the conclusions).

### 4.2 Proposed conservative timing convention (design, not yet implemented)

Given the mechanics above, for a **daily** signal built from BTC/ETH raw-chain or vendor-derived aggregates:

1. **Signal window**: define day *D* by **block timestamp**, UTC calendar day, using the *last block whose timestamp falls within [D 00:00:00, D 23:59:59] UTC*. Because BTC timestamps can drift up to +2h into the "future" relative to true receipt time (§4.1), a block timestamped 23:50 on day D could in rare cases have been received/broadcast after midnight D+1 — this is bounded and small, but not zero, so it must be treated as a source of label noise, not ignored.
2. **Confirmation/finality buffer before computing anything for day D**:
   - **BTC**: require the day-D-closing block plus **≥6 confirmations** (~60 min) before treating any day-D block as immutable input to the signal, consistent with the classical safety margin and comfortably covering the largest documented historical reorgs (53 blocks in 2010, 24+ in 2013 — those are extreme tail events from an immature network, not a basis for a much deeper buffer today, but a reminder that "settled" is probabilistic, never absolute).
   - **ETH (PoS)**: require the day-D-closing block to be **finalized**, i.e. wait for the **2nd epoch checkpoint after D's close to justify** (≈12.8 minutes under normal operation) — and additionally build in slack for finality-delay incidents like May 2023 (up to 9 epochs ≈ 57.6 minutes observed) by not hard-computing until either finality is confirmed via a beacon-chain finality checkpoint check, or a fixed fallback buffer (e.g. 2 hours) has elapsed, whichever is later.
3. **Vendor/provider publication lag**: add each provider's own stated latency on top of the chain-native buffer — e.g. Glassnode's 00:00–03:00 UTC daily computation window, Coin Metrics' "within 5 minutes of interval close" claim (itself only as reliable as its own infra that day — use the `AssetCompletionTime`/`AssetEODCompletionTime` completion-flag metrics, where available, to gate on rather than trusting a fixed clock offset), or AWS's ETH-specific ~01:45 UTC nightly compaction.
4. **Computation cutoff**: do not begin computing day-D's signal until **max(chain finality buffer, vendor publication buffer)** has elapsed past D's UTC close. Concretely this argues for a cutoff of **D+1 03:00–06:00 UTC** as a conservative default across BTC+ETH+typical vendor latency (covers Glassnode's up-to-03:00 UTC window, AWS's 01:45 UTC ETH compaction, and multiple confirmation/finality buffers with margin).
5. **Fixed execution time**: execute strictly on a **fixed wall-clock time on D+1** (e.g. **D+1 08:00 UTC**, chosen to sit safely after the D+1 06:00 UTC computation cutoff with a further operational margin for provider outages/incident-driven delays like the May 2023 finality events) — never execute "as soon as data looks available," since that reintroduces exactly the non-monotonic-timestamp and provider-latency risk this convention exists to control.
6. **Reorg/revision handling**: recompute day-D's signal value if the chain-data provider later republishes a revised value for day D (Coin Metrics' `flash`/`reviewed`/`revised` status flags are built for exactly this; AWS/BigQuery data should be treated as append/overwrite-on-correction and diffed against prior pulls) — log both the original and revised value rather than silently overwriting, to preserve an audit trail for point-in-time correctness testing.

This is a design proposal for Stage 1+ implementation, not a finding to promote — it should be encoded as executable causal-alignment tests (per AGENTS.md core rule #2 and CLAUDE.md's "implement tests for causal alignment and execution semantics") before any signal code is written against it.

## Decision-relevant conclusions

1. **Bitcoin address-level daily metrics (active addresses, tx count, value transferred, fees) are reconstructable from raw chain data with known, well-documented caveats** (P2PK/bare-multisig/OP_RETURN have no or ambiguous address semantics; clustering heuristics are imperfect and specifically broken by CoinJoin; Lightning volume is invisible; Ordinals/BRC-20/Runes since 2023–2024 add spam-like, protocol-aware activity that naive parsers will miscount as ordinary transactions). None of these caveats are new or fatal — Coin Metrics, Glassnode, and open-source ETL tooling all ship metrics built on the same imperfect heuristics — but they mean a from-scratch reconstruction will not be "more correct" than existing vendor series unless the specific caveat being targeted (e.g. explicitly excluding OP_RETURN, or explicitly flagging Ordinals-era transactions) is the actual point of the research.

2. **Ethereum's reconstruction problem is categorically different and harder for anything beyond raw transactions/logs**: EOA-vs-contract conflation, token transfers living in logs rather than native transfers, internal transactions requiring historical-state replay (traditionally archive-only), and the 2024+ L2/blob migration all mean an L1-only, transaction-only view increasingly misrepresents "Ethereum economic activity" as time progresses through the sample.

3. **The single biggest practical finding of this audit**: `s3://aws-public-blockchain` (confirmed anonymously listable, MIT-0 licensed, current in 2026, open-source ETL provenance) already ships exactly the hardest-to-reconstruct tables — BTC `transactions` with **input addresses/values pre-resolved** (no local prevout/UTXO tracking needed) and ETH `logs`/`token_transfers`/**`traces`** (internal transactions, no local archive node needed) — as ordinary daily Parquet partitions, at a measured 2021-06-15 volume of ~488 MB/day (BTC tx) and ~1.53 GB/day (ETH traces), i.e. full-history (2015–2024) pulls are feasible from this machine's disk budget only via selective/columnar access (Athena or filtered S3 reads), not bulk download of every table. This converts the D1 question from "can we afford to run an archive node" (no, not on 244 GB free) to "can we afford to read a vendor-transformed but open-methodology dataset via Athena" (yes) — with the residual risk being AWS's own "experimental, not for production" disclaimer and the fact that we have not independently audited that specific ETL run's correctness against our own node.

4. **The Coin Metrics Community API is a metadata/aggregate source, not a raw-reconstruction source**, and is missing exactly the two metrics (`AdrNewCnt`, `TxTfrValAdjNtv`) most likely to matter for a "new address" or "adjusted transfer value" style feature — those would require either the paid Coin Metrics tier or independent reconstruction from raw/AWS data.

5. **Dune's free tier lost API access as of 2026-09-10** (mid-audit-relevant news, worth flagging since prior team knowledge may assume free Dune API access still exists) — it is now view-only unless paid ($75+/month).

6. **Timing design is dominated by three independent, additive delay sources, not one**: Bitcoin's own ±(MTP, +2h) timestamp slack, Ethereum's ~12.8-minute (or occasionally much longer — up to ~1 hour observed in the May 2023 incident) PoS finality latency, and vendor-side computation/publication windows (Glassnode up to 03:00 UTC, AWS ETH ~01:45 UTC). A conservative causal-execution convention — cutoff at D+1 03:00–06:00 UTC, execute at a fixed D+1 08:00 UTC — comfortably dominates all of these individually and should be encoded as an explicit, testable rule before any Phase 11B Stage 1 signal is coded, consistent with AGENTS.md's "no lookahead... impossible same-bar fills" rule.

7. **Open items flagged UNVERIFIED, not to be treated as settled facts**: the exact Bitcoin Core version that introduced `getblock` verbosity=3 (conflicting evidence for 0.22.0 vs 23.0); the exact current BTC stale/orphan-block rate; the "~4-minute" BigQuery `crypto_ethereum` latency claim; era/era1 file hosting location; Blockchair's actual (vs. advertised) anonymous accessibility (this session's live fetch returned HTTP 401). None of these block the Stage 0 conclusion, but none should be cited elsewhere in the research program as confirmed without a follow-up primary-source check.
